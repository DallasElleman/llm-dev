# Report types — sub-domains and prompt skeletons

Each type lists the sub-domains it fans out into. At **standard** depth dispatch one agent per sub-domain. At **quick**, merge a type's sub-domains into one agent. At **deep**, add the extra angles listed.

Every prompt = the block from `report-craft.md` (read-only constraint + calibration + seeds + method) **plus** the type-specific body below. Adapt the file paths to the project — the examples are illustrative, not fixed.

---

## 1. Code quality, security & efficiency — 6 sub-domains

**1a. Auth & authorization.** Login flows, token/session lifecycle, cookie flags, session fixation and revocation, MFA/passkeys, password storage. Enumerate every privileged route and check the gate is applied consistently. Hunt IDOR by changing an ID. Check CSRF on every state-changing endpoint. Look for auth bypass via header trust or dev-mode shortcuts live in prod.

**1b. Injection, XSS, SSRF, uploads, secrets, transport.** Every string-built query — separate constant interpolation from user-reachable. Every HTML sink and whether escaping is consistent. Every user-supplied URL fetch: DNS rebinding, redirect revalidation, private-IP and metadata-endpoint blocking. Uploads: magic bytes vs. declared type, path traversal, size and decompression limits, where files are served from. Secrets in tracked files (including archived logs and transcripts — a common leak channel), in CI config, in error responses. Security headers and CSP. If the project calls an LLM: prompt injection from untrusted content into prompts that drive privileged action, output validation, cost controls on unauthenticated endpoints.

**1c. Language-level code quality.** Module cohesion and god-modules — say which large files are *fine* (a big migrations file is normal; a big app entrypoint may not be). Layering violations against the project's own stated conventions. Error handling and swallowed exceptions. Real duplication, verified. Typing and linter config. Dead code — verify with grep before claiming. Worst functions by length and nesting.

**1d. Frontend code quality.** Module system and global namespace. State management coherence. Render strategy and DOM thrash. Listener leaks (compare add vs. remove — and check whether non-removed ones are actually correct). Network layer: dedup, abort, retry, caching, waterfalls. Error handling and offline behavior. Asset delivery: compression, cache headers, request count, bundling — check the served headers, don't assume.

**1e. Data-layer efficiency.** Trace round trips per request on the hot paths and **count them**. N+1s with estimated trip counts. Indexes: dump the schema, cross-reference against actual WHERE/JOIN/ORDER BY, report missing *and* unused. Query shape, payload size, compression, caching and cache invalidation. Startup cost and what blocks boot. Concurrency: worker/thread config, shared mutable state, background threads.

**1f. Tests, CI/CD, deps, ops.** **Run both suites and report actual output** — never a result you didn't observe. Coverage gaps by risk, not percentage. Test quality: over-mocking, structure-vs-behavior tests, flakiness sources, shared mutable fixtures. CI: does it run everything, on what triggers, and can a failing test reach production — trace this precisely. Dependency pinning and reproducibility. Container: size drivers, root, healthcheck, cold start. Observability: what would the team see if a route started 500ing?

*Deep adds:* threat model against the actual deployment; a load-ceiling estimate from worker config × per-request cost.

## 2. Architecture & product — 6 sub-domains

**2a. Product intent vs. implementation.** Read the PRD/specs/roadmap and any user-feedback source. State the core value proposition in a paragraph. Inventory subsystems: which serve the value prop, which are speculative, which are complexity generated by a *prior architectural choice* rather than user need. Sample ~10 features and trace each to a real requirement; quantify how much is self-generated. Compare shipped work against stated scope and priority order. If build volume dwarfs usage, say so directly and read what it means.

**2b. Infrastructure fit.** Enumerate every constraint the platform imposes that a conventional one wouldn't. **Quantify the workaround cost** — count files, LOC, workflow steps, and runbooks that exist only to cope with it. Find the original rationale in history or docs; check whether its premises still hold. Lay out 3–4 concrete alternatives with effort, monthly cost at current *and* projected scale, what code gets deleted, and new risks. Give a recommendation, not a menu.

**2c. Data model & storage.** Does the implemented schema match the spec, and is divergence principled or drift? Is the storage engine right at this data volume and shape? Is bespoke database/driver code a liability, and what would it take to delete? Legacy tables and their row counts.

**2d. Search / ML / heavyweight subsystems.** Is the machinery justified at the actual corpus size? Find or build an evaluation and **measure the delta** against a simpler baseline — the result is often "the expensive component ties the cheap one." Check whether a lighter runtime produces identical output. Separate quality problems from *content* problems: a search stack tuned against a corpus missing the target domain is a data task, not a retrieval task.

**2e. Frontend architecture & UX.** Where is the current approach's ceiling and how close is the code? Trace the actual user journey from the code — cold open, primary flows — and assess friction. Measure first-load weight. Does internal vocabulary leak into user-visible strings? What do empty states show with no data? Options from cheapest to most invasive, with a recommendation and what happens to existing tests.

**2f. Counterfactual.** State requirements free of the current implementation's vocabulary. Design 3 genuinely distinct target architectures — a radically simpler one, a conventional one, and an evolutionary one. For each: what's deleted, kept, new; effort in engineer-weeks; cost at both scales; onboarding impact; top 3 risks. Then **one recommendation, no hedging**. Be honest about rewrite risk and sunk cost.

*Deep adds:* process/maintainer-reality pass — contributor distribution from git, bus factor, whether process weight matches the team that actually exists.

## 3. Coherence sweep — 6 sub-domains

**3a. Doc→code drift.** Extract every *testable* claim the docs make about the code and check it: commands that should run, files that should exist, routes that should respond, counts, module purposes, config defaults, conventions asserted as followed. Report compliance **rates**, not just violations. Also report the inverse: load-bearing behavior documented nowhere.

**3b. Doc→doc contradiction.** Test whether the declared source-of-truth hierarchy actually holds. Look hardest for contradictions *internal* to one document — the append-a-correction-and-leave-the-original pattern. Check whether the decision log contradicts the body text elsewhere in the same file.

**3c. Superseded-as-current.** For every plan/spec/roadmap: is its work done, abandoned, or live — and does anything mark that? Test blind: pick three files and try to determine status without git history. Measure delete rates per surface; an append-only documentation layer is the root cause, not a symptom. Classify the "current state" index files and check they agree.

**3d. Code-internal incoherence.** Competing implementations of one concept — say which is canonical. Conventions declared vs. practiced, and for each decide whether to **fix the code or fix the rule** (this distinction matters and is usually missed). Comments that disagree with their code. Naming incoherence across layers — build a concept→names table. Constants duplicated across a language boundary, and which are parity-tested. Tests that exercise dead code.

**3e. Reference integrity.** Script it; enumerate rather than sample. Markdown links, anchors, bare paths in prose, `file:line` refs (check the line still says what's claimed), section refs, symbol refs, cross-references in comments, commit SHAs, issue refs, symlinks, and the tracked/gitignored boundary. Report counts by failure mode. Recommend a lightweight recurring check — and be specific about **false-positive sources**, which determine whether such a check survives its first week.

**3f. Vocabulary & decision-log integrity.** Concept→names map across schema, backend, frontend, UI strings, and docs. Which splits are principled (a real distinction, or a deliberate compat shim with an owner and an end date) versus accidental drift — **do not recommend "fixing" a principled one**. Does internal vocabulary leak into user-visible strings? Then: for each logged decision, does it still hold? Find silent reversals and logged-but-unimplemented ones. Find major architectural choices in force that were never logged at all, and decisions whose stated rationale has since expired.

## 4. Dependency & supply chain — 3 sub-domains

**4a. Resolution & reproducibility.** Resolve the true dependency graph **for the deployment target, not the host** — this is where naive checks silently produce wrong answers, because platform filters often apply to artifact selection while environment markers still evaluate against the local machine. Verify the resolve reflects the target before trusting it. Lockfile presence, pin tightness, host↔CI↔prod drift.

**4b. Vulnerabilities & weight.** Query a vulnerability database for the resolved set, and **spot-check that results are actually version-filtered** rather than returning everything for the package. Compare the deployment resolve against the local environment — the gap is the reproducibility risk, made concrete. Flag advisories whose fix is unreachable under current pins. Size drivers and unnecessary heavy transitive deps.

**4c. Provenance & licensing.** Unpinned or mutable third-party CI actions, especially with write permissions. Jobs that install dependencies while holding secrets. Licence compatibility. Whether any scanning exists at all.

## 5. Onboarding & contributor experience — 3 sub-domains

**5a. Cold-start path.** Actually run the documented setup on a clean copy. Every command, every prerequisite, every credential. Find where it breaks or silently half-succeeds — **half-success is worse than failure** and is common in seed/bootstrap paths that latch a "done" flag on partial state. Time it. Note anything requiring a personal account or secret.

**5b. First contribution path.** Is there a labeled starter issue, and does the labeling convention the docs cite actually exist? Trace change → test → review → merge. Where does someone without repo context stall? Check whether the contribution guide matches reality.

**5c. Knowledge architecture.** Would a new contributor find what's current? Is generated/agent output curated or accumulating? Is institutional knowledge tracked in git or only on someone's machine (check for untracked-but-cited material). What survives the primary maintainer leaving — enumerate credentials and services and who owns them, flagging any that fail *silently*.

## 6. Pre-launch / operational readiness — 4 sub-domains

**6a. Data safety.** Are backups automated or aspirational? Has a restore ever been executed? Migration rollback story. Any ephemeral-storage trap where user data silently disappears on restart.

**6b. Failure behavior.** What breaks first under load — compute the concurrency ceiling from worker config and per-request cost, and state it as a number. Which failures are silent. What the team would see, and how fast, when a route starts erroring. Health endpoint, alerting, rollback time.

**6c. Day-one experience.** With no usage data, what does every surface show? Empty states, cold-start latency, first-load weight on a mobile connection. Does the value proposition land in five seconds?

**6d. Go/no-go.** A ranked list of what must be true before real users arrive, separating genuine blockers from things that can follow. Be willing to say it's ready.

## 7. Accessibility & inclusive design — 3 sub-domains

**7a. Structure & semantics.** Semantic elements vs. div soup. Heading hierarchy. Landmarks. Custom controls: does each implement the ARIA pattern it advertises — **announcing a role without implementing its keyboard behavior is worse than plain markup**. Live regions scoped tightly, not wrapping whole panels.

**7b. Interaction.** Full keyboard operability. Focus management for modals, sheets, pickers, route changes — check focus trap, focus-in, and focus restore *per surface*, since partial application is the norm. Focus visibility. Touch target sizes. Whether state changes are announced, not just styled.

**7c. Perception.** Contrast against the real token values in both themes. Information conveyed by color alone. Text scaling and zoom reflow. `prefers-reduced-motion` — check it's honored in the animation engines, not just declared in CSS. Alt text. Media captions.

*Deep adds:* a screen-reader walkthrough of the primary flows, reported step by step.
